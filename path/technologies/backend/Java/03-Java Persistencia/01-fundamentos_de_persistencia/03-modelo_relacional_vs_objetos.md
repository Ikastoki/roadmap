# Modelo relacional vs objetos

El desarrollo de software empresarial convive con dos paradigmas de representacion de datos fundamentalmente distintos. El codigo fuente se escribe en lenguajes orientados a objetos (Java, C#, Python) donde los datos se agrupan en objetos con estado y comportamiento, organizados en jerarquias de herencia, asociaciones y composiciones. El almacenamiento persistente, por su parte, esta dominado por el modelo relacional: tablas, filas, columnas, claves foraneas y restricciones de integridad. La tension entre ambos mundos se conoce como impedancia objeto-relacional (object-relational impedance mismatch).

## Diferencias fundamentales

**Tipos de datos.** El modelo relacional tiene un conjunto fijo de tipos (INTEGER, VARCHAR, DATE, BOOLEAN, etc.), mientras que Java ofrece tipos primitivos, objetos inmutables (String, BigDecimal), enumeraciones, colecciones (List, Set, Map), Optional y tipos compuestos definidos por el usuario. No existe correspondencia directa para muchos tipos Java en SQL: un `Map<String, String>` no tiene equivalente relacional natural; un `Optional<LocalDate>` debe traducirse a una columna nullable; un `enum` puede mapearse a VARCHAR o INTEGER.

**Identidad.** En el modelo relacional, la identidad de una fila se establece mediante una clave primaria (una o varias columnas). Dos filas con la misma clave primaria son la misma fila, independientemente de sus demas valores. En Java, la identidad de un objeto se define por su direccion de memoria (identidad de referencia) o por la implementacion de `equals()`/`hashCode()`. Un ORM debe conciliar ambas nociones: dos objetos Java cargados desde la misma fila de base de datos pueden ser la misma instancia (managed) o instancias distintas (detached), lo que introduce problemas de igualdad y actualizacion.

**Relaciones.** Las relaciones en SQL se expresan mediante claves foraneas y tablas intermedias (N:M). En Java, las relaciones son referencias entre objetos: una clase `Pedido` contiene una referencia a `Cliente` (1:N), y `Cliente` puede contener una coleccion de `Pedido`. La direccion de navegacion importa: en SQL se navega mediante JOINs, mientras que en objetos se navega siguiendo punteros. Un ORM debe traducir estas referencias a consultas JOIN, gestionar la carga perezosa (lazy loading) para evitar traer toda la base de datos a memoria, y sincronizar los cambios en ambos sentidos.

**Granularidad.** Una clase Java puede representar conceptos finos (una direccion como objeto Value Object) que en SQL suelen estar embebidos en la misma tabla que la entidad propietaria. El modelo relacional tiende a la normalizacion (dividir en tablas separadas para evitar redundancia), mientras que el modelo de objetos favorece la agregacion (composicion de objetos dentro de otros). La decision de mapear un Value Object como una tabla separada (embedded vs entity) es una de las decisiones mas recurrentes al disenar el mapeo ORM.

## Soluciones a la impedancia

**ORM (Object-Relational Mapping).** Herramientas como Hibernate, EclipseLink o OpenJPA automatizan la traduccion entre ambos mundos. El desarrollador anota las clases Java con metadatos (@Entity, @Column, @OneToMany) y el ORM genera el SQL, gestiona el estado de las entidades, sincroniza los cambios y mantiene una cache de identidad. La ventaja es la productividad: el codigo trabaja con objetos puros y el ORM oculta la complejidad relacional. El inconveniente es la perdida de control sobre el SQL generado, la dificultad de depurar problemas de rendimiento (N+1 queries) y la complejidad del modelo de ciclo de vida (managed, detached, removed).

**SQL manual.** El enfoque opuesto consiste en escribir SQL directamente con JDBC o MyBatis. El desarrollador controla exactamente que consultas se ejecutan, con que indices y en que orden. No hay generacion automatica de SQL, no hay lazy loading, no hay cache de identidad que pueda dar sorpresas. La desventaja es la cantidad de codigo repetitivo (boilerplate) necesario para mapear manualmente cada fila a un objeto y viceversa.

**Enfoque hibrido.** Frameworks como MyBatis o jOOQ ocupan un termino medio: ofrecen mapeo automatico de resultados SQL a objetos Java, pero el desarrollador escribe las consultas manualmente. jOOQ va un paso mas alla generando un DSL tipado que refleja el esquema de la base de datos, permitiendo escribir consultas SQL con type-safety en Java.

## Como JPA/Hibernate resuelven la impedancia

JPA ataca cada punto de friccion con mecanismos especificos. Para los tipos de datos, proporciona un conjunto de convertidores (`@Converter`, `AttributeConverter`) que permiten transformar cualquier tipo Java en una columna SQL y viceversa. Para la identidad, define el concepto de `@Id` y estrategias de generacion de claves (IDENTITY, SEQUENCE, TABLE), junto con la cache de primer nivel (PersistenceContext) que garantiza que dos accesos a la misma fila dentro de la misma transaccion devuelvan la misma instancia Java. Para las relaciones, ofrece anotaciones `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany` con configuracion de carga (FetchType.LAZY vs EAGER), cascada de operaciones (CascadeType) y mapeo de tablas intermedias via `@JoinTable`. Para la granularidad, proporciona `@Embeddable` y `@Embedded` que permiten embeber objetos Java como columnas dentro de la misma tabla.

Ninguna solucion es perfecta. El ORM introduce una capa de abstraccion que filtra en momentos criticos (consultas complejas, actualizaciones masivas, esquemas no normalizados). Conocer la impedancia objeto-relacional y las herramientas que ofrece JPA para resolverla es requisito indispensable para disenar un mapeo eficiente y evitar los problemas de rendimiento que surgen cuando el ORM genera SQL ineficiente sin que el desarrollador sea consciente de ello.
